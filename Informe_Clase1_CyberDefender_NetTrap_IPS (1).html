2. Entregable 1 · Ficha de Idea y Alcance

Herramienta: NetTrap-IPS

Problema que resuelve:
Centralizar la recolección de eventos de tráfico anómalo en una red local con Windows, correlacionar escaneos de reconocimiento en tiempo real y automatizar el aislamiento en el firewall antes de que se consume una intrusión.

Tipo: Analizador de logs de red

Alcance:
1. Monitoreo constante y escucha activa en puertos trampa (señuelos) para registrar de inmediato cualquier intento de conexión.
2. Motor de correlación en tiempo real para detectar patrones de escaneo rápido (SYN scan con Nmap) y accesos no autorizados.
3. Respuesta automatizada de contención aplicando reglas dinámicas Allow/Deny en Windows Defender Firewall (lógica practicada en natted.cloud).
4. Registro forense centralizado e invocación de TShark para exportar capturas .pcap asociadas a cada incidente crítico detectado.

Exclusiones:
1. No dejará que el atacante interactúe a fondo (No es un servidor falso completo):
La trampa no es un sistema operativo vulnerable donde el atacante pueda subir archivos o ejecutar comandos de verdad. Solo abre el puerto, detecta que tocaron la puerta, captura la IP y cuelga la llamada de inmediato.

2. No descifrará tráfico web seguro (No rompe TLS/HTTPS):
La herramienta vigila qué IP se conecta y a qué puerto llama, pero no va a descifrar conversaciones seguras o contraseñas encriptadas por dentro (no hace inspección profunda de paquetes).

3. No protege toda la red de la universidad, solo el equipo donde corre:
No va a cambiar las configuraciones de los routers Cisco ni los switches del laboratorio. Solo controla el Firewall de Windows del computador donde está instalado el programa.

4. Entregable 3 · Requisitos de Seguridad

4.1. Funcionales

RF-01 Recolectar eventos desde al menos 3 fuentes distintas: Windows Event Log (canales Security y System), Firewall de Windows y Nmap/TShark.
Ingesta de eventos de las 3 fuentes en tiempo real y visualización en el dashboard en menos de 5 segundos desde su generación.

RF-02 Normalizar todos los eventos a un formato único (JSON) con los campos obligatorios: timestamp, origen, severidad, evento, ip_origen y descripcion.
Todo evento almacenado en la base de datos cumple el esquema JSON definido. Los eventos mal formados se rechazan y se registran en un log de errores.

RF-03 Correlacionar eventos mediante reglas configurables en formato YAML (ej.: "5 fallos de login desde la misma IP en 60 segundos → alerta crítica").
El motor evalúa cada evento entrante contra las reglas activas y genera una alerta cuando se cumple la condición definida.

RF-04 El SIEM debe alertar al administrador en tiempo real a través de notificaciones en el propio dashboard/sistema desarrollado (vía WebSockets / Server-Sent Events o push nativo) cuando se dispare una regla de severidad 'alta' o 'crítica'
La notificación emerge en la interfaz del dashboard en menos de 3 segundos e incluye: IP, evento, severidad y hora

RF-05 Exponer un dashboard web con autenticación que muestre eventos recientes, estadísticas por fuente/severidad y reglas activas.
El dashboard solo es accesible tras login válido y refresca los datos cada 10 segundos sin recargar la página.

Logging de auditoríaSe registran todas las acciones críticas: login exitoso/fallido, creación/edición de reglas, inicio/detención del servicio, emisión de alertas y cambios en configuración. Los logs son append-only (no editables ni borrables por usuarios normales) y se guardan en un archivo separado con hash de integridad.OWASP ASVS V8.1.1 / ISO 27033

Contacte al administrador&quot;). Nunca se exponen stack traces, rutas de archivos ni nombres de variables internas en el dashboard o respuestas HTTP.OWASP ASVS V7.1.1 / V7.4.1

Las IPs se validan con regex estricta (IPv4/IPv6). Las reglas YAML se validan con esquema (jsonschema). Se aplica whitelist (no blacklist) y se escapan salidas HTML para prevenir XSS.OWASP ASVS V5.1.1 / V5.2 / V5.3
